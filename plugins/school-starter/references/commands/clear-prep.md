# Clear準備コマンド

コンテキストをクリアする前に、**詳細な**引き継ぎ用のメッセージをターミナルに出力します。

## 重要なルール

- **引き継ぎテキスト本体（詳細版）はファイル作成せず、ターミナルに直接出力する**
- **加えて、`000_PROJECT_STATUS.md` に要約版（15行以内）を上書き保存する**（手順2参照。VS Code やパソコンを閉じる人の引き継ぎが消えないように）
- 「学びの還元」は引き継ぎテキスト出力**前に** `/learn` スキルに従って `~/.claude/docs/best-practices.md` / `error-solutions.md` / `skill-health.md` に追記する（やり忘れで学びが消えないように）
- ユーザーがコピペして /clear 後に貼り付けられる形式にする
- **次のClaudeが困らないように、詳細に記載する**

## 手順0: 学びの有無をチェック（最初に必ず実行）

引き継ぎテキストを作る前に、セッション全体を振り返って **保存すべき新規の学びがあるか** を判定する。

### 判定フロー

1. **セッション内容を振り返る** - 以下の知見を発見したか？
    - エラーを2回以上試行して解決した（試行錯誤あり）
    - 新しいライブラリ・パターン・ツール・APIの使い方を発見
    - 上手くいかなかったアプローチがあった（アンチパターン）
    - スキル実行で品質低い・手動修正が必要だった
    - 案件固有のドメイン知識を発見

2. **該当なし** → **何もしない**。引き継ぎテキストの「💾 自動保存した学び」セクションには **「なし」** とだけ記載して終了。ファイル読み込みも追記もしない。

3. **該当あり** → 既存ファイル（`~/.claude/docs/best-practices.md` / `error-solutions.md` / `skill-health.md`）を grep で重複チェック → 既存と重複していれば追記しない → **本当に新規の学びだけ**追記する。

### 追記先

| 検出する知見 | 追記先 |
|------------|--------|
| エラーを2回以上試行して解決した | `~/.claude/docs/error-solutions.md` |
| 新しいライブラリ・パターン・ツール・APIの使い方を発見 | `~/.claude/docs/best-practices.md` |
| 上手くいかなかったアプローチ（アンチパターン） | `~/.claude/docs/best-practices.md`（注意点・落とし穴） |
| スキル実行で品質低い・手動修正が必要だった | `~/.claude/docs/skill-health.md` |

詳細フォーマット・重複排除ルールは `/learn` スキルを参照。

### 出力ルール

- 実際に追記したものだけを「💾 自動保存した学び」セクションに記載する
- 何も追記しなかった場合は「なし」とだけ記載
- **「念のため空ファイル touch」「テンプレ追記」のような無駄な書き込みは絶対にしない**

## 手順1: git の状態を実測する（出力直前に必ず実行・記憶で書かない）

引き継ぎの「📍 現在の状態」は**会話の記憶ではなく実測値**で書く。以下を実行してから出力する:

```bash
git status -sb          # 未コミット変更 + origin との ahead/behind
git log --oneline -3    # 最後のコミット
```

- **理由**: 受講生は push を VS Code の「↑」ボタンで行うため、**push はセッションの外で起きる**。会話の記憶だけで書くと「未 push」が古い情報になり、次セッションの Claude が誤った最優先タスク（push）を実行しようとする
- `git status -sb` の `ahead` 表記がなければ push 済み。`ahead N` なら未 push N 件
- remote（origin）が未設定のプロジェクトでは ahead/behind は出ないので「remote 未設定」と書く
- 注: この判定は**同一マシンで push した場合に正確**（push 成功時にローカルの origin 参照も更新される）。別マシンからの push までは反映されないが、`git fetch` は**実行しない**（sandbox オン環境では認証で失敗し得るため。受講生運用は同一マシンなので実用上十分）

## 手順2: 000_PROJECT_STATUS.md に要約版を上書き保存

ターミナル出力（詳細版）とは**別に**、`docs/000_PROJECT_STATUS.md` に**要約版を上書き保存**する。VS Code やパソコンを閉じてもファイルと Git に引き継ぎが残るようにするため。

### 書き方

1. ファイル内の `<!-- HANDOVER-START -->` 〜 `<!-- HANDOVER-END -->` マーカーを探す
2. **あれば**: マーカーの間を今回の内容で**丸ごと置換**（前回分は残さない・追記しない）
3. **なければ**: 「📍 現在地」セクションの直後にマーカーごと新設する
4. `000_PROJECT_STATUS.md` 自体が存在しないプロジェクトでは、この手順をスキップして引き継ぎテキストにその旨を記載

### 要約版フォーマット（YOU MUST: 15行以内厳守）

```markdown
<!-- HANDOVER-START -->
## 📨 前回セッションからの引き継ぎ（YYYY-MM-DD）

- **現在地**: [フェーズ/何が終わったか1行。最後のコミット hash と push 済み/未 push（手順1の実測値）]
- **次にやること**: [最優先タスク1-2個。具体的に]
- **注意・保留**: [保留事項・既知の制約を1-3個。なければ「特になし」]
- **詳細の参照先**: [git log / 関連 docs など、深掘りが必要なときに見る場所]
<!-- HANDOVER-END -->
```

- **15行を超えない**。PROJECT_STATUS の主役はタスク管理なので、引き継ぎが長いと「今どこ？」が埋もれる
- ファイル一覧・技術的決定・学びの詳細は書かない（git log・docs・best-practices.md から再取得できる。要約版は「現在地と次の一手」だけ）
- 詳細版（下記フォーマット全文）はターミナル出力のみ。**ファイルには書かない**

## 出力フォーマット

以下の形式でターミナルに直接出力してください。**各セクションは省略せず、詳細に記載すること**：

## 詳細記載のガイドライン

### なぜ詳細が必要か
- /clear 後のClaudeは**何も覚えていない**
- 省略された情報は**失われる**
- 詳細であればあるほど、スムーズに作業を再開できる

### 特に詳しく書くべきこと
1. **ファイルパス**: 必ず絶対パスで記載
2. **意思決定の理由**: なぜその選択をしたか
3. **試行錯誤の過程**: 何を試して何がダメだったか
4. **現在の状態**: ビルド・テスト・サーバーの状態
5. **次のアクション**: 具体的に何をすべきか

### 省略してはいけないこと
- 作成したファイルの一覧
- 変更したファイルの一覧
- 技術的な決定事項
- エラーや問題が発生した場合はその詳細

## 手順（全体の流れ）

1. 手順0: 学びの有無をチェック → あれば永続化
2. 今回の会話内容を**全て**振り返る
3. 手順1: git の状態を実測する（`git status -sb` / `git log --oneline -3`）
4. 手順2: `000_PROJECT_STATUS.md` の HANDOVER マーカー間に要約版（15行以内）を上書き保存
5. 上記フォーマットで**詳細な**引き継ぎメッセージをターミナルに直接出力する（詳細版はファイルに書かない）
6. 末尾で「続けて作業する場合（コピペ再開）/ 今日はここまでの場合（そのまま閉じてOK）」の2択を案内する
