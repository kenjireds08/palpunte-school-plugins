# AI 駆動開発の標準フロー（マスタープレイブック）

> 未来AI学院 上級コースで提供するアプリ開発の**全体フロー**。
> 受講生は「次は何をすればいい？」と迷ったら**このファイルの該当フェーズに戻って確認**する。
>
> AI（Claude Code）も、フェーズ判定や次アクション提案のときは**まずこの全体図に立ち返る**。

## このプレイブックの位置づけ

スクール上級コースは「Claude Code でアプリを 1 本作って納品できるようになる」のがゴール。
そのための**標準フロー**を 4 フェーズに整理した。

| フェーズ | やること | 主な道具 |
|---------|---------|---------|
| **0. 要件定義** | 何を作るかを言葉で固める | `/interview-light` / `/interview-full` + Codex 4-7R |
| **1. 進捗管理 3 階層構築** | プロジェクトを「動かせる単位」に分解する | `/school-starter:project-flow`（自動展開） |
| **2. タスク実装ループ** | 1 タスクずつ実装 → レビュー → 動作確認 | Plan Mode / `/feature-dev:feature-dev` / `review` / Codex |
| **3. 納品前総合チェック** | 本番に出す前の最終ゲート | `/school-starter:pre-delivery-check` + `@agent-security-auditor` |

各フェーズには「**いつ次に進むか**」の判定基準がある。**前フェーズが完了するまで次に進まない**のが鉄則。

## フェーズ 0: 要件定義（迷いゼロの土台）

### ゴール
**「誰が、何を、なぜ使うか」を 1 ページの仕様書に固める**。ここが曖昧なまま進むと、後の全工程で迷子になる。

### 標準ステップ

1. **`/new-project` で初期化**
   - フォルダを作って `claude` 起動 → `/new-project` 実行
   - 案件状態（受注確定 / 相談段階 / 自分用）を答える
   - `CLAUDE.md` / `docs/000_PROJECT_STATUS.md` / `docs/001_requirements.md` 等が自動生成される

2. **要件ヒアリング**
   - **受注前 / モックアップ用** → `/interview-light`（5 問完結・15 分）
   - **受注後 / 本実装用** → `/interview-full`（9 観点詳細・60-90 分）
   - 出力先: `docs/001_requirements.md`

3. **Codex 第三者レビュー（4-7R 通称: 4R + 7R）**
   - 要件定義が固まったら**実装に入る前に必ず**別タブの Codex CLI（または ChatGPT）に投げる
   - `docs/001_requirements.md` の中身を貼って「この要件定義に抜け漏れ・矛盾・暗黙の前提がないか指摘して」と依頼
   - 4 回（4R: 4 ラウンド）または 7 回（7R: 7 ラウンド）まで対話して**Codex が「概ね問題なし」と返すまで反復**
   - 反映 → `docs/001_requirements.md` を更新 → ステータスを「確定」に

### 完了判定
- [ ] `docs/001_requirements.md` のステータスが「確定」になっている
- [ ] Codex レビューで Critical 指摘が 0 件
- [ ] 受講生本人が「これで何を作るか言える」状態

### よくある罠
- ❌ 要件定義をスキップして「とりあえず動かしてみる」 → 後で全部やり直しになる
- ❌ Claude 単体のレビューで満足する → 同じモデル系統では盲点が残る（Codex 必須）
- ❌ 要件定義書を Markdown で書いて満足 → クライアント案件は HTML or Google Docs で渡す

## フェーズ 1: 進捗管理 3 階層構築（project-flow 自動展開）

### ゴール
要件定義 → **動かせる単位（タスク）に分解**された 3 階層ドキュメント体制を作る。

### 3 階層構造

```
000_PROJECT_STATUS.md       ← 全体俯瞰（フェーズ進捗・残タスク数）
  ├─ 007_task_backlog.md    ← T-XX 単位の作業手順書
  └─ 008/009/010 個別 md    ← DB 設計 / セキュリティ設計 / API 設計（必要時のみ）
```

### 標準ステップ

1. **要件定義完成後、Claude が自動提案**
   ```
   要件定義が完成しました 🎉 次は「進捗管理 3 階層」を一気に展開します。
   project-flow スキルが自動で 5-10 分で展開します。OK ですか？
   ```

2. **OK と返すと `/school-starter:project-flow` が自動発火**
   - `000_PROJECT_STATUS.md` 更新（フロントマター + 進捗チェックボックス）
   - `007_task_backlog.md` 生成（30-50 タスクが標準・1 タスク = 半日〜2-3 日）
   - 個別 md（DB / セキュリティ / API）は要件定義スキャンで自動判定して生成

3. **3 階層展開直後の Codex 最終ゲート（必須）**
   - 展開された 3 階層を別タブの Codex に投げて「タスク粒度・依存関係・抜け漏れ」をレビュー
   - これを通さずに実装に入ると、**Phase B5 以降で「タスク粒度バラバラ問題」「依存逆転問題」が surface する**

### task_backlog の書き方（YOU MUST）

各 T-XX には**必ず以下を含める**（`task-backlog-template.md` 参照）:

- **目的**: なぜこのタスクが必要か（要件のどの項目を満たすか）
- **依存**: 前提となる T-XX
- **作業手順**: 番号付きの具体ステップ
- **完了条件 (DoD)**:
  - 機能要件（要件定義の該当項目）
  - 動作確認（dev サーバー / 手動操作）
  - テスト（lint / typecheck / build）
  - **3 段階レビュー実施**（Phase B5 以降は必須・Phase B3-B4 は規模に応じて）
  - **実機検証**（本番デプロイを伴うタスクは必須）
  - ドキュメント更新

### 完了判定
- [ ] `007_task_backlog.md` に 30-50 タスクが並んでいる
- [ ] 各 T-XX が「半日〜2-3 日」の粒度に揃っている
- [ ] Codex 最終ゲートを通過済み

## フェーズ 2: タスク実装ループ（1 タスクずつ確実に）

### ゴール
**1 タスク完了 → コミット → 次のタスク**を確実に回す。**並行実装はしない**（Phase 完走前の集約レビューで盲点が surface するため）。

### 1 タスクのライフサイクル（全規模共通）

```
① 規模判定 → ② 計画 → ③ 計画レビュー → ④ 実装 → ⑤ 3 段階レビュー → ⑥ 実機検証 → ⑦ コミット
```

### ステップ詳細

#### ① 規模判定
| 規模 | 判定基準 | 計画方式 |
|------|---------|---------|
| **簡単** | 1-2 ファイル / typo / 単純な追加 | そのまま実装 OK |
| **中規模** | 3 ファイル以上 / ロジック変更あり | **Plan Mode**（Shift+Tab）で計画 |
| **大規模** | 設計判断複数 / 認証・RLS・DB スキーマ変更 / 新機能まるごと | **`/feature-dev:feature-dev`** で並列専門家設計 |

#### ② 計画
- Plan Mode: その場で計画を提示 → 承認待ち
- /feature-dev: code-explorer / code-architect / code-reviewer が並列で動いて設計書を作る

#### ③ 計画レビュー（中規模以上は必須）
- Plan / 設計書を**別タブの Codex CLI** に貼って「この計画に抜け漏れ・矛盾・暗黙の前提がないか」レビュー
- 反映 → 計画を更新 → 承認

#### ④ 実装
- 計画に従って 1 タスク分のコードを書く
- **依頼された内容のみ実装**（過剰な機能追加・抽象化をしない・development.md 参照）

#### ⑤ 3 段階レビュー（中規模以上は必須）
**順序厳守**:
1. **`@agent-security-auditor`**（OWASP / 認証 / RLS / 暗号化観点）
2. **`/school-starter:review`**（feature-dev:code-reviewer 内部レビュー → 5 回ループ）
3. **Codex 独立レビュー**（出力サマリーを別タブにコピペ）

各段階で **Critical が出たら必ず修正してから次へ**。

#### ⑥ 実機検証（第 4 のレビュー段階・本番デプロイを伴うタスクは必須）
- ブラウザ DevTools Console を開いて red error 0 件
- Vercel Function Logs を確認
- 主要フロー 1 周を手動操作
- **CSP / フォント / Vercel Cron 等の環境依存設計**は静的解析で見えないので**ここで初発見されるのが正常**

#### ⑦ コミット
- `git status` で意図したファイルだけステージ確認
- `git commit` → CI / pre-commit hook 通過確認
- `000_PROJECT_STATUS.md` のチェックボックスと `007_task_backlog.md` の状態列を ✅ に更新

### Phase 完走前の「集約レビュー」（IMPORTANT）

各 Phase（B3 / B4 / B5 / B6 / B7）の最後のタスク完走前に、**Phase 内の全変更をまとめて Codex に独立レビュー**してもらう。

**理由**: Codex 軸の予測不能性は**文脈単位**で発現する。「触っていないコード」が他タスクと組み合わさったときに Medium 級の指摘が surface することを Phase B5 開発で実証済み。**「Codex は前タスクで OK だったから集約は不要」は禁止**。

### 完了判定
- [ ] 全タスク（007_task_backlog.md）が ✅ になっている
- [ ] 各 Phase の集約レビューを通過済み
- [ ] 受け入れテスト（DoD チェックリスト）全項目通過

## フェーズ 3: 納品前総合チェック（最終ゲート）

### ゴール
**コードの中身は OK でも、設定・運用・引き渡しでミスがあれば本番事故になる**。最後のゲートで全部塞ぐ。

### 標準ステップ

1. **`@agent-security-auditor` で全体監査**
   - Phase 2 で各タスク単位ではやったが、**全体に対しても 1 回**かける
   - OWASP Top 10 / 認証 / RLS / 暗号化 / 入力検証

2. **`/school-starter:pre-delivery-check` で 10 項目チェック + 実機検証**
   - 個人開発 / クライアント案件で分岐
   - 10 項目（環境変数 Sensitive / .env git 履歴 / npm audit / セキュリティヘッダー / RLS 目視 / service_role 棚卸し / 規約 URL / 引き渡しパッケージ / OAuth App / 無料プラン pause）
   - **第 4 のレビュー段階「実機検証」5 項目**（v1.16.0〜・本番 URL での主要フロー / DevTools Console / Vercel Logs / メール実機到達 / 環境依存設計目視）

3. **最終レポート出力 → クライアント / 自分への引き渡し書類化**

### 完了判定
- [ ] @agent-security-auditor で Critical 0 件
- [ ] pre-delivery-check の 10 項目 + 実機検証 5 項目すべて FAIL 0 件
- [ ] レポートを Notion / Google Docs に保存

## 全フェーズ共通の鉄則

### 1. 計画を承認するまでコードを書かない
- Plan Mode / /feature-dev / 要件定義のいずれも**承認後に実装**
- 「とりあえず動かしてみる」は要件定義フェーズの段階以外では禁止

### 2. 第三者レビュー（Codex）を省略しない
- 要件定義 → 計画 → 実装 → 納品前の**節目すべて**で Codex を通す
- Claude 単体は同じモデル系統で盲点が残る（Codex 必須の経済合理性は Phase B5 9 タスク連続実証済み）

### 3. 1 メッセージ = 1 ステップ（受講生対応時）
- 受講生（非エンジニア）相手に 5 ステップ一気出ししない
- 「今やるべきこと = この 1 つだけ」を明示
- 詳細: `claude-md-template.md` の「受講生向けハンズオン中の振る舞い」Rule 1-4

### 4. 必須最小限を判断して提示
- 機能を提示する前に「**今この受講生に必須か / 将来必須か / 不要か**」を分類
- 必須のみを最初の 1 メッセージに / 将来必須は予告のみ / 不要は省略

### 5. 自分が踏んだ地雷をルール化する
- エラー解決・新パターン発見・アンチパターン発見時は `/school-starter:learn` で蓄積
- 信頼度 2 以上に昇格したら CLAUDE.md / rules / Hook 化を検討

### 6. 環境変数追加時は 3 箇所同期（v1.16.0〜）
- `.env.local`（実値・git 管理外）
- `.env.example`（ダミー値・git にコミット）
- Vercel ダッシュボード（Sensitive ON）
