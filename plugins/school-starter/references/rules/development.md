# 開発ルール

## 開発原則
- 要件定義を最優先
- 既存パターンを踏襲
- テスト実行後にデプロイ
- 複雑なタスクは3-5段階に分割
- エラー発生時は最大3回まで試行
- 依頼された内容のみ実装し、過剰な機能追加・抽象化をしない
- 推測でコードを提案せず、必ず該当ファイルを確認してから回答する
- **判断にだけ AI を使う**: 分類・要約・抽出には Claude を使ってよい。ただし**決定論的処理**（リトライ判定、ステータスコード分岐、フォーマット変換）はコードで書く。コードで答えられる問いはコードで答えさせる
- **規約衝突は平均化せず surface する**: コードベース内に矛盾する 2 つのパターンが共存している場合、両方を満たそうとして混ぜたコードを書かない。**新しい方・テスト済みの方を選び、もう一方を cleanup フラグとして報告**する
- **Fail loud**: 「完了」「pass」「成功」を簡単に言わない。スキップしたレコード・実行しなかったテスト・確認していないエッジケースは**明示的に surface**する。不確実性は隠さず可視化する

**詳細:** CLAUDE.md 設計の全体像は `/school-starter:claude-md` スキルで参照可能（Karpathy 4 ルール + @mnilax 追加 8 ルール / 30 codebase × 6 週間でミス率 41% → 3% の実証データ）。

## コード実装前の必須確認
- 類似の既存コードを確認
- コードスタイル・命名規則を踏襲
- 既存のユーティリティを活用

## セキュリティ
- .envファイルはコミットしない
- APIキーはVercel環境変数で管理
- 認証情報をログに出力しない

## テストコマンド
```
npm run lint       # lint
npm run typecheck  # 型チェック
npm test           # テスト
npm run build      # ビルド
npm run check      # 一括実行（あれば）
```

## 検証ルール
実装完了後は検証コマンドを実行し、エラーがなくなるまで修正すること

## 受講生向けハンズオン中の振る舞い 4 ルール（v1.16.0〜・YOU MUST・全コンテキスト適用）

IMPORTANT: 受講生（GAS / Excel 経験者レベル・非エンジニア前提）にハンズオン手順を案内する文脈では**全タスク横断で以下 4 ルールを厳守**する。AI が「網羅的に案内する」自然な傾向で受講生の学習意欲が折れる事故を防ぐ。詳細とメタファーは `claude-md-template.md` の同名セクション参照。

### Rule 1: 1 メッセージ = 1 ステップ
- 5 ステップ手順を見つけたら最初の 1 ステップだけ表示し「この 1 つを完了したら報告してください」と明示
- 「Claude 作業」「受講生作業」「並行可」が 1 メッセージに混在しない

### Rule 2: 非エンジニアでもわかる言葉
- 専門用語の前に**1 文で言い換え**を添える（例: 「allowlist（許可リスト）」「Sensitive（秘密扱いフラグ）」）
- 手順は「画面の場所 → クリック → コピー → 貼る」レベルまで具体化
- コピペ対象は必ず `----ここから---- / ----ここまで----` で囲む

### Rule 3: 受講生作業 vs Claude 作業の境界明示
- 各ステップ冒頭に「**▶ あなたが作業 / ◀ Claude が作業**」マーカーを置く
- 並行作業を提案しない（授業中は同期優先）

### Rule 4: 必須最小限を判断して提示
- 機能を提示する前に「今この受講生に必須か / 将来必須か / 不要か」を分類
- 必須のみを最初の 1 メッセージに / 将来必須は予告のみ / 不要は省略
- プラン制約（Free / Pro 必須等）も**今の受講生のプランに合わせて判断**

**根拠**: T-62 Vercel デプロイ準備で 1 日 4 回再発（信頼度 3 🔴 確定）。「網羅的に案内する」「全部詰め込む」AI の自然な傾向は明示ルール化しないと再発する。

## 環境変数追加時は 3 箇所同期（v1.16.0〜・YOU MUST）

新しい環境変数を追加するときは、**`.env.local` だけ更新して終わらない**。以下 3 箇所を必ず同期する:

1. **`.env.local`**: 実値追記（受講生が別ターミナルで手動）
2. **`.env.example`**: ダミー値追記して git にコミット（引き継ぎ用変数一覧）
3. **Vercel ダッシュボード**: 本番デプロイ前に登録（Sensitive ON）

**根拠**: `.env.example` 漏れは引き継ぎ・別 PC 環境構築・pre-delivery-check のすべてで再発する構造的問題。新しい変数を追加する瞬間に同期を案内するのが唯一の予防策。

## git push は VS Code の「↑」ボタンを案内する（v1.23.0〜・YOU MUST）

- **Claude は `git push` を自分から提案・実行しない**（「git push 一発です」と言わない）。push が必要な場面では「**VS Code 左側のソース管理ビューの「↑」ボタン（変更の同期）**を押してください」と案内する
- 理由①（主）: 受講生が「何が GitHub に公開されるか」を**自分の指で押して意識する習慣づけ**（第8回の Vercel 本番公開への伏線）＋ コピペシートの案内（↑ ボタン）と Claude の案内を**一致**させるため
- 理由②（技術）: **sandbox をオンにしている環境**では credential helper（macOS Keychain / Windows 資格情報マネージャー）へのアクセスが deny され認証エラーになる。sandbox オフ（auto mode 等）では通ることもあるが、**通る/通らないが環境依存**なので案内は ↑ ボタンに統一する
- **例外**: ユーザーが**明示的に**「push して」「gh でリポジトリを作って push まで」と頼んだ場合は、**1回だけ試してよい**（「環境によっては認証エラーになります」と前置きし、失敗したら無理に回避せず別ターミナル用コマンドを提示する）。リポジトリ新規作成（`gh repo create --source=. --push` 等の初回セットアップ）はこの例外の典型
- `git add` / `git commit` / `git status` / `git diff` / `git log` は Claude 内で常に OK
- VS Code のボタンで push された結果は Claude のセッションからは見えない。**push 済みかどうかを報告するときは `git status -sb` で実測してから**書く（記憶で「未 push」と書かない）
  - 注: この実測は**同一マシンで push した場合に正確**（push 成功時にローカルの origin 参照も更新されるため。受講生運用は同一マシンなので実用上十分）。別マシンからの push や GitHub 上の直接編集までは反映されないが、確認のための `git fetch` は**必須にしない**（sandbox オン環境では fetch も認証で失敗し得るため）。厳密さが必要な場面では「ローカルの origin 参照基準では push 済み」と限界を添えて報告する

**根拠**: 第4回通し検証（2026-06-11）で「git push 一発です」提案 → sandbox オン環境では失敗する事故パターンを確認。2巡目（2026-06-12・sandbox オフ）では gh repo create / push とも成功を実測し、**可否は環境依存**と確定。だからこそ案内は「↑ ボタン」に統一し、実行は明示依頼時の1回試行に限定する。

## 実装プランは docs/plans/ にファイル化して Codex ゲートを通す（v1.24.0〜・YOU MUST）

タスクバックログ（`docs/{NNN}_task_backlog.md`）があるプロジェクトで実装タスクに着手するときの標準フロー:

1. **プラン作成**: `docs/000_PROJECT_STATUS.md` と task_backlog の該当タスクを読んでから、Plan Mode 等で実装計画を立てる
2. **配置確認**: Plan Mode のプランは `plansDirectory: "./docs/plans"` 設定（setup 手順 1-10）により **`docs/plans/` に自動保存される**。承認後、ファイル名がタスクと結びつかない場合は **`docs/plans/<タスクID>-plan.md`** にリネームする（例: `docs/plans/T-02-supabase-setup-plan.md`）。Plan Mode を使わず自分でプランを書く場合も同じ場所・同じ命名で保存する。`~/.claude/plans/` などプロジェクト外には置かない（同じフォルダで開いている Codex から読めなくなるため）
3. **Codex ゲート**: 次の依頼文をコピペ用に案内する:
   「`docs/plans/<ファイル名>` を読んで、`docs/000_PROJECT_STATUS.md` と `docs/{NNN}_task_backlog.md` の該当タスクと突き合わせて、実装計画として妥当かレビューしてください。指摘には severity（critical/high/medium/low）を付け、問題なければ approve と明言してください」
4. **実装**: Codex approve 後に実装 → 完了後は 2 段階コードレビュー（review スキル）
5. **後片付け**: タスク完了時にプランを `docs/plans/archive/` へ移動し、PROJECT_STATUS / task_backlog を更新する

- `docs/plans/` は **git 管理に含める**（履歴・引き継ぎ・別 PC で効く）。`.claude/plans/`（内部用・gitignore 対象）とは別物
- **スキップ条件**: 1〜2 ファイル・数十行以内の軽微な修正はプランファイル不要（Plan Mode の承認だけで実装してよい）。Phase 規模・複数ファイル・DB 変更を伴うタスクで使う
- これで Codex ゲートは「要件定義 → **実装プラン** → 実装後コード」の3箇所に揃う（作る前に2回・作った後に1回）

## create-next-app が生成する AGENTS.md は削除を勧めない（v1.24.0〜）

- AGENTS.md は「Next.js 16 は AI の学習データから変わった部分がある」という AI 向け注意書きで、CLAUDE.md から `@AGENTS.md` で参照する設計。**「CLAUDE.md と役割が重複するので削除しても OK」と提案しない**（コピペシートの案内「消さずにそのままで OK」と矛盾して受講生が混乱する。第4回検証で2回連続発生）
