# テスト・lint改ざん防止ルール

## このルールが守るもの（先に読む）

**このルールが禁じているのは「既存の見張りを弱めること」だけ**です。
**新しく見張りを増やす作業（CI の新設・lint ルールの追加・pre-commit フックの作成）は対象外**で、
むしろ推奨されます。対象パスに入っているからという理由だけで、**新規作成をためらわないでください**。

- ✅ OK: `.husky/pre-commit` を**新しく作る** / CI に検査を**足す** / lint ルールを**厳しくする**
- ❌ NG: 既存のフックを**消す・素通りさせる** / CI の検査を**外す** / lint ルールを**緩める**

判断に迷ったら「**この変更で、検査は厳しくなるか緩くなるか**」を自問してください。厳しくなるなら進めてよい。

## 絶対にやらないこと（例外は"事前に相談して承認を得る"）

- テストを通すために、テストを弱めない
  - skip/only化、アサーション削除、期待値の雑な書き換え、スナップショット乱用
- lint/formatを通すために、ルールや設定を弱めない
  - eslint/prettier/tsconfig 等の設定緩和、lint コマンドや scripts の差し替え
- Husky/CI を通すために、フックやワークフロー設定を弱めない
  - .husky/** や .github/workflows/** の "抜け道化"

## 例外が必要なときの手順（必須）

1. 変更が必要な理由（仕様変更/誤ったテスト/フレーク等）を文章で説明
2. 変更対象ファイルと差分要約を提示
3. ユーザーの明示承認を待つ（承認なしに変更しない）

## 基本方針

- 失敗している場合は、原則「実装」を直してテスト/lintを通す
- テストは "仕様"。仕様が変わらない限りテストを緩めない
