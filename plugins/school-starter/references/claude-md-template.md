## 大きな開発依頼への自動提案ルール

受講生から以下の依頼を受けたときは、**いきなり実装を始めず、先に提案する**:

- 「◯◯アプリを作って」「◯◯機能を丸ごと追加して」など大規模な新機能依頼
- 3 ファイル以上を触る必要がありそうな変更
- 設計の選択肢が複数ありそうな機能追加
- 既存コードの調査が必要な複雑な変更

### 判断フロー

1. **何を作るかがまだ曖昧 / 設計判断が必要** → **`/feature-dev` を提案**
   - 提案例: 「この開発は大掛かりなので、まず `/feature-dev` で設計フェーズから始めますか？ code-explorer / code-architect / code-reviewer の 3 つの専門家が並列で動いて、既存コード調査 → 設計案比較 → レビューまで一気通貫でやってくれます」
   - **`/feature-dev` の出力後は Codex で第三者レビューを提案する（実装前の重要ゲート）**: 「設計書ができました。実装前に別 AI（Codex）に第三者レビューしてもらうことを強く推奨します。/feature-dev は内部で全て Claude 系統なので盲点が残る可能性があります」と案内し、Codex CLI 別タブに設計書のパスを渡してレビュー依頼してもらう
2. **何を作るかは決まっている / 実装直前の最終確認だけ欲しい** → **Plan Mode（Shift+Tab）を提案**
3. **単純なバグ修正・1〜2 ファイルの小変更** → どちらも不要、直接実装してよい

### 原則

- **迷ったらまず提案する方向に倒す**。非エンジニアの受講生は「大きな変更」を気軽に依頼してくるので、Claude 側が「まず計画を」と提案することで暴走や手戻りを防ぐ
- **計画を承認するまでコードを書かない**
- 提案するときは「なぜそれを使うと良いのか」を 1〜2 行添える（受講生が機能を理解しながら使えるように）

## 授業中の振る舞い（同期優先）

IMPORTANT: スクール授業中は **「効率」より「同期」を優先**する。AI 駆動開発として並行作業（外部サービスの設定を講師に依頼している間に独立タスクを進める等）は正しいが、**スクール授業文脈では全員が同じ画面を見て同じ手を動かすのが最優先**。

- 外部サービス（Supabase / Resend / Vercel 等）のアカウント作成・設定は、講師に任せきりにせず**受講生本人が同じ操作を体験する**前提で進める
- 「講師が ◯◯ を作っている間に並行で △△ を進めましょうか？」という提案を**しない**（受講生を置いていく原因）
- 例外: 講師から「今は並行で進めて OK」と明示された場合のみ並行作業に入る

理由: 受講生は実装フローを「手を動かして覚える」段階。並行作業で時短しても、外部サービス設定や設定値の意味が体験できないと第8回以降のデバッグで詰まる。

## Plan Mode と /feature-dev の使い分け

- **Plan Mode**（Shift+Tab）: 実装直前の作業確認（軽量・即時。計画を承認したらそのまま実装に入る）
- **/feature-dev**: 要件定義・設計判断が必要なフェーズ（複数の専門エージェントが並列で動く重めの処理。設計文書をファイルとして残す）

## 判断を求めるときは AskUserQuestion を使う

- 選択肢が 2 つ以上ある決定（実装方針・ライブラリ選定・設計案・Plan Mode 分岐等）
- 推奨項目に `(Recommended)` / 選択肢は 2〜4 個 / 単純 Yes/No や 1 択では使わない

## フロントエンド UI 実装時のルール

フロントエンド UI 実装を始める時、以下の 2 ファイルを必ず読んでから着手する:

- `~/.claude/docs/design-md-template.md` — DESIGN.md カタログ（awesome-design-md-jp 24 サービス + jp-ui-contracts 5 プロファイル + 実運用 Tips）。プロジェクト性格に合った参考サービスを選び、`DESIGN.md` をプロジェクトルートに配置する
- `~/.claude/docs/ui-prohibited-patterns.md` — AI っぽさ排除のチェックリスト（紫グラデ・カード上端カラーバー・`shadow-lg` 多用・`text-black` 等の典型パターンを避ける）
- 入力 UI は特に `<input type="date">` `<input type="time">` を書きそうになった瞬間に ui-prohibited-patterns.md の「フォーム」セクションを必ず確認（OS / ブラウザ依存で統一感がないため、shadcn Calendar+Popover ベースのカスタムコンポーネントを使う）

## デプロイ

- GitHub に push → Vercel 自動デプロイ
- Vercel CLI は使用しない（安全性重視）

## git ルール

- `git push --force` は禁止（main / master はツールレベルで deny 済み、その他ブランチも非推奨）
- 代わりに `git push --force-with-lease` を使う（同僚のコミットが上書きされる事故を予防）
- コミット前に `git status` で意図したファイルだけステージされているか確認

## セキュリティ

IMPORTANT: `.env` の値をチャットに表示しない（存在確認のみ OK）。

- 詳細: `~/.claude/rules/env-security.md`
- `.env` ファイルはコミットしない / API キーは Vercel 環境変数で管理 / 認証情報をログに出力しない
- Supabase RLS チェックリスト: `~/.claude/rules/supabase-security.md`（migrations/ や *.sql 編集時に paths で自動ロード）

## 納品前の 3 段階レビュー

YOU MUST: 納品前は必ず**3 段階レビュー**を実施する（第 7 回・第 10 回で使う）。**順序**:

1. `@agent-security-auditor` で OWASP Top 10 / 認証 / RLS / 暗号化観点の独立監査（先に専門観点で筋を通す）
2. `review` スキル（`feature-dev:code-reviewer` による品質・ロジック・見落としの内部レビュー + 最大 5 回の自動修正ループ）
3. 出力された「作業サマリー」を別タブの Codex CLI または ChatGPT にコピペして第三者独立レビュー

**すべての段階で 🔴 Critical が出ないこと**を確認してから納品物を確定する。

## セキュリティチェック系の曖昧発話への対応

受講生はセキュリティチェックのコマンドを覚えられない前提で動く。「セキュリティチェックして」「納品前に見て」「これ安全？」「公開して大丈夫？」「認証まわり確認して」「RLS 合ってる？」「Supabase のポリシー見て」「脆弱性ないか確認して」「漏洩してない？」等の発話が来たら、Claude は専門コマンドを叩かせず以下のフローで対応する:

1. AskUserQuestion で意図確認: 「**納品前のセキュリティチェックですか？**」（選択肢: (1) 全面監査 / (2) 直近変更だけ / (3) 特定機能だけ（認証・RLS 等））
2. 受講生が返答したら、`@agent-security-auditor` を呼び出して監査を実施

NG: 受講生の曖昧発話を無視して Claude 自身でチェックを始める / 「セキュリティは重要です」のお題目だけで終わらせる / 受講生に専門コマンドを覚えさせる。
