# dependency-pr — 部品の更新提案（PR）が届いたときの進め方

## 最初に伝えること（受講生を落ち着かせる）

Dependabot（部品の見張り）は、アプリが使っている他人製の部品に新しい版が出たり弱点が見つかったりすると、**「更新しませんか」という提案を自動で作ります**。これが PR（プルリクエスト）です。

受講生に必ず先に伝える3点:

1. **これは事故ではありません。** 見張りがちゃんと働いている証拠です
2. **今すぐ対応しなくても壊れません。** 提案が置いてあるだけで、取り込むまで今のアプリは何も変わりません
3. **1件ずつ見ます。** まとめて一気に取り込むのが、いちばん危ない進め方です（後述）

## 大原則: まとめて一気にマージしない

**実際に起きた事故**: 11 件の更新提案をまとめて取り込んだ結果、本番へ配信する仕組みが壊れ、**丸1日以上、直した内容が1つも本番に反映されない**状態になりました。しかもテストは全部緑で、画面も普通に動いて見えたため、誰も気づきませんでした。

だから、**1件取り込む → 本番に出たか確かめる → 次の1件**、の順で進めます。急ぐ理由はありません。

## STEP 1: 何の提案なのかを見る

受講生に GitHub の画面を開いてもらう（`gh` コマンドは使わなくてよい。使える環境なら Claude が代わりに読んでもよい）:

> GitHub のリポジトリのページ → 上のタブの「**Pull requests**」

タイトルの読み方を案内する:

| タイトルの例 | 意味 |
|---|---|
| `chore(deps): bump ○○ from 1.2.3 to 1.2.4` | 本番でも使う部品の更新 |
| `chore(deps-dev): bump ...` | 開発中だけ使う部品の更新（比較的安全） |
| `ci(deps): bump actions/... ` | 自動検査の仕組み自体の更新 |

**数字の読み方**（受講生はここを知らない）:

- `1.2.3` → `1.2.4` = **いちばん右だけ変化**。小さな修正。比較的安全
- `1.2.3` → `1.3.0` = **真ん中が変化**。機能追加。ふつうは安全だが確認する
- `1.2.3` → `2.0.0` = **いちばん左が変化**。大きな変更。**壊れる前提で確認する**
- ⚠️ **`0.` で始まるもの**（例 `0.5.2` → `0.6.0`）は例外。**まだ完成前の部品なので、小さな更新でも平気で壊れます**。左が変わったのと同じくらい慎重に扱う

## STEP 2: 自動検査（CI）が ✅ か ❌ か

PR のページの下のほうに、検査の結果が出ています。**ここが最初の分かれ道**です。

### ❌ の場合 — マージしない

**この赤は「見張りが仕事をした」という意味**です。取り込んでいたら壊れていたものを、手前で止めてくれました。受講生に「失敗した」と思わせないこと。

Claude がやること:

1. どの検査が落ちたかを確認する（型／lint／ビルドのどれか）
2. 原因を調べて、**受講生の言葉で**説明する
3. 対応を提案する（下の「よくある2パターン」を参照）

そのうえで、**多くの場合の正解は「今は取り込まない」**です。PR は閉じずに置いておき、あとで別の対応と一緒に片付けます。慌てて直そうとして本体のコードをいじらないこと。

**よくある2パターン**（実案件で実際に起きたもの）:

| 症状 | 何が起きているか | 対応 |
|---|---|---|
| 型の検査が落ちる | 部品側で「使い方の決まり」が変わった。今のコードの書き方が通らなくなった | 取り込むなら**こちらのコードも直す**必要がある。1タスクとして別に立てる |
| lint が「起動しない」形で落ちる | 検査の道具自体の更新で、**設定の書き方が変わった**。放っておくと「検査しているつもりで、実は何も検査していない」状態になる | 特に重要。設定の直し方を Claude が調べて対応する。**放置は禁物** |

### ✅ の場合 — ただし、まだマージしない

緑は「**今のテストでは問題が出なかった**」という意味であって、「安全だと確認できた」ではありません。次の STEP へ進みます。

## 【重要】「本番」と「確認用」を混同しない — メールが来ても慌てない

受講生が**いちばんパニックになるポイント**なので、PR の話をするときは必ずここを先に説明する。

Vercel は**2種類のデプロイを作る**。名前が紛らわしいだけで、意味はまったく違う。

| 種類 | いつ作られる | 誰が見るもの | 失敗したら |
|---|---|---|---|
| **本番（Production）** | `main` に取り込まれたとき | **お客さん・実際の利用者** | 🚨 対応が必要 |
| **確認用（Preview）** | PR ごと（提案のブランチ） | 自分だけ。URL も別 | ✅ **むしろ好都合** |

**確認用は「この提案を取り込んだらどうなるか」を先に試すお試し版**です。だから——

> **PR 側（確認用）が失敗しても、お客さんが見ている本番はまったく無事です。**
> それどころか、**取り込む前に問題が分かった**ということなので、見張りが正しく働いた結果です。

Vercel から「Deployment failed」というメールが届いても、まず**どちらが失敗したのか**を確認する。件名やページに出ているブランチ名が `dependabot/...` なら確認用なので、慌てる必要はまったくない。

### 赤い場所によって、意味が正反対になる

- **確認用が赤い** → 「この提案は今のコードと相性が悪い」というお知らせ。取り込まなければよいだけ。**セーフ**
- **本番が赤い** → 直したものが**本番に届いていない**。画面は動いて見えるので気づきにくい（最後に成功した状態を配信し続けるため）。**こちらは要対応**

受講生に伝える一言:

> **「赤い＝失敗」ではなく、「どこが赤いか」で意味が変わります。**

## STEP 3: 何が変わるのかを確認する

PR の説明欄に、部品の作者が書いた変更内容（Release notes / Changelog）が展開できる形で載っています。Claude がこれを読んで、**受講生に3行で説明する**:

1. この部品は、このアプリの**どこで使われているか**
2. 今回の更新で**何が変わるのか**
3. このアプリに**影響がありそうか / なさそうか。その理由**

分からないときは「分からない」と正直に言う。そのうえで「見送る」を選べばよい。**無理に判断しない**。

**特に丁寧に見るもの**: 左の数字が変わる更新 / `0.` で始まる部品 / 画面の見た目に関わる部品（グラフ・UI 部品など。テストが通っても**見た目だけ崩れる**ことがあり、これは自動検査では捕まりません）

## STEP 4: 判断の理由を PR にコメントで残す

**このスキルでいちばん大事な習慣です。**

AI に作業させると「やりました」で終わりがちですが、**なぜそう判断したかが残っていないと、後から検証できません**。3か月後に不具合が出たとき、「あのときなぜ取り込んだんだっけ」を追えるようにしておきます。

PR のコメント欄に、こういう短いものを残す（Claude が下書きして、受講生が貼る）:

```
確認した内容:
- 自動検査: ✅（型・lint・ビルドすべて通過）
- 変更内容: 〇〇の不具合修正。このアプリでは△△の画面で使っている
- 影響: 使い方の決まりは変わっていないため、影響なしと判断
→ マージします
```

見送る場合も同じように残す:

```
確認した内容:
- 自動検査: ❌（型の検査が落ちた）
- 原因: 部品側で使い方の決まりが変わり、□□.tsx の書き方が通らなくなった
→ 今は取り込まない。コード側の対応をタスクとして別に立てる
```

## STEP 5: マージする

GitHub の PR ページの「**Merge pull request**」ボタンを押します（`gh` コマンドは使わない）。

マージ後、手元を最新にするのを忘れないよう案内する: VS Code のソース管理から「プル（↓）」、または Claude に「最新を取り込んで」と頼む。

## STEP 6: 本番に出たかを確かめる（省略禁止）

**ここを飛ばすと、冒頭の事故と同じことが起きます。**

「テストが通った」と「本番に出た」は別ものです。マージしたら必ず:

1. デプロイ先（Vercel など）のダッシュボードを開く
2. **「本番（Production）」の**最新のデプロイが**成功しているか**を見る（確認用の結果ではなく、本番のほうを見る）
3. 本番の画面を開いて、主要な操作が動くかを1つ試す

ここまでやって1件完了です。**次の PR に進むのは、ここが確認できてから**。

## 何もしないとどうなるか

- **溜まるだけで、アプリは壊れません。** 気力のあるときにまとめて片付けても構いません（ただし取り込むのは1件ずつ）
- ただし **「弱点が見つかった」という警告つきの更新は放置しない**。GitHub の Security タブに出ているものは優先して対応する
- 毎週届くのが煩わしい場合は、`.github/dependabot.yml` の受け取り間隔を `weekly` から `monthly` に変える手もある（提案してよい）

## やらないこと（受講生に踏ませない地雷）

- **「とりあえず全部マージ」をしない。** 冒頭の事故そのもの
- **CI を赤いまま放置して、他の作業を続けない。** 赤が普通の状態になると、本当の異常に気づけなくなる
- **検査を通すために、検査のルール自体を緩めない。** それは「見張りの目隠し」であって解決ではない（詳細は `~/.claude/rules/test.md`）
- **強引な回避策を採らない。** 部品の版を無理やり書き換えて辻褄を合わせる方法（`overrides` 等）は、動いて見えても品質が保証されない。取り込めないなら見送るのが正解

## このスキルがやらないこと

- 品質ゲートそのものの導入 → `quality-gate` スキルの担当
- コードの脆弱性診断 → `@agent-security-auditor` の担当
- 納品前の総合チェック → `pre-delivery-check` スキルの担当
