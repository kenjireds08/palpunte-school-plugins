# /learn スキル — 知見の自動蓄積

セッション中に得た知見を、適切な保存先に自動で追記する。
**ユーザーが言わなくても発火する**。同じ知見の重複は避ける。

案件をこなすほど、Claude Code が自分専用の知識ベースを蓄積していく仕組み。

## 自動発火トリガー（重要）

以下を検知したら、その場で発火する。`/clear` を待たない。

| トリガー | 保存先 |
|---------|--------|
| エラーを2回以上試行して解決した（試行錯誤あり） | `~/.claude/docs/error-solutions.md` |
| 新しいライブラリ・パターン・ツール・APIの使い方を発見 | `~/.claude/docs/best-practices.md` |
| 上手くいかなかったアプローチがあった（アンチパターン） | `~/.claude/docs/best-practices.md`（注意点・落とし穴） |
| スキル実行で品質低い・手動修正が必要だった | `~/.claude/docs/skill-health.md` |
| 案件固有のドメイン知識を発見（その案件でしか使わない） | そのプロジェクトの `CLAUDE.md` を提案（書き込みは確認後） |

## グローバル vs プロジェクトの判断

| 判定 | 保存先 |
|------|--------|
| 他プロジェクトでも使えそう | グローバル（best-practices.md / error-solutions.md） |
| この案件のドメイン特有 | プロジェクトCLAUDE.md（書き込み前に確認） |
| 迷ったら | **グローバル**（後で整理できる） |

## 重複排除と信頼度スコア（重要）

**YOU MUST**: 追記前に**必ず保存先を grep して既存パターンと照合**する。これを飛ばすと、同じパターンが何回起きても新規エントリ追加だけ続き、信頼度昇格 = CLAUDE.md/Hook 化への昇格判定が機能しなくなる。

### grep の具体手順（必須）

新規追記候補が決まったら、追記前に以下を必ず実行:

1. **主要キーワード3つを抽出**（スキル名・カテゴリタグ・問題の核心ワード）
   - 例: ある投稿スキルの再発検知なら `["投稿スキル名", "テンプレ", "_template"]`
   - 例: Supabase RLS の Storage upsert 失敗なら `["Supabase", "RLS", "Storage", "upsert"]`
2. **保存先ファイルを `grep -E "<keyword1>|<keyword2>|<keyword3>"`** で全件チェック
3. **ヒットしたエントリの中身を Read** して、本質的に同じパターンか判定:
   - 同じスキル/同じ症状/同じ根本原因 → **既存エントリの信頼度++ で完了**（新規追記しない）
   - 別の症状/別の根本原因 → 新規エントリ追加 OK
4. **判定根拠を1行ログ**: 「grep 結果 N件ヒット → 既存エントリ ### XXX と同パターン → 信頼度++」 or 「grep 結果ヒットなし → 新規追記」

### 新規パターン（grep で既存ヒットなし）
- そのまま新規エントリとして追記
- フォーマットの末尾に `(信頼度: 1)` を付ける（**省略不可**）

### 既存パターンに該当（grep で既存ヒットあり）
- **新規エントリは追加しない**
- 既存エントリの信頼度を上げる:
  - `(信頼度: 1)` → `(信頼度: 2 ⚠️ 再発)`
  - `(信頼度: 2)` → `(信頼度: 3 🔴 強い知見)`
  - `(信頼度: 3 以上)` → そのまま（既に確立した知見）
- 既存エントリの **発生日に再発日を追記**（例: `2026-05-10 → 2026-05-10（同日2回目）, 2026-05-15（再発）`）
- 既存エントリの **教訓・対処に新情報があれば追記**（同じエントリ内に統合）

### 信頼度の意味
| スコア | 意味 | 扱い |
|-------|------|------|
| 1 | 1回観測 | 参考情報（他案件で再発するか様子見） |
| 2 ⚠️ 再発 | 2回観測 | 同じパターンが再発 → **CLAUDE.md / rules 化を検討** |
| 3 🔴 強い知見 | 3回以上 | **CLAUDE.md / rules / Hook 化を強く推奨** + weekly-checklist で月次レビュー |

**理由**: ECC (Everything Claude Code) の instinct システムと同じ思想。1回限りの偶発的な出来事と、繰り返し起きる本質的なパターンを区別することで、本当に重要な知見を浮き上がらせる。

### grep スキップは即実害につながる（実例）

**よくある失敗**: 1回目に「テンプレと実装の乖離」を新規追記 → 同日中に同じ系統の問題が再発 → grep を飛ばして **別エントリとして新規追加**してしまう。

**正しい対応**: 2回目発生時に grep で既存エントリ発見 → **信頼度: 1 → 2 ⚠️ 再発 に昇格 + 既存エントリの教訓欄に2回目の情報を統合**。新規エントリは作らない。

この失敗を放置すると信頼度昇格機構が機能せず、weekly-checklist 月次レビューで「CLAUDE.md/Hook 化検討」のトリガーが発火しなくなる。

### その他のルール
1. 既存の記載が古い・不完全なら **更新**（日付を新しくする、信頼度++）
2. カテゴリが不明な場合は「その他」に追記

## 発火時の手順

### Step 1: 知見を分類
上記トリガー表で保存先を決定。

### Step 2: 既存ファイル確認
保存先ファイルを Read し、類似パターンがないか確認。

### Step 3: 追記

各ファイルのフォーマットに従って追記。

> ⚠️ **必須ルール**: 新規追記時は**必ず信頼度スコア `(信頼度: 1)` を末尾に付ける**。これがないと重複排除と昇格判定が機能しない。

#### error-solutions.md フォーマット
```markdown
### [カテゴリ] エラーの簡潔な説明
- **発生日**: YYYY-MM-DD
- **案件**: プロジェクト名
- **エラー**: エラーメッセージ（核心部分のみ）
- **失敗したアプローチ**: 試して駄目だった方法（箇条書き）
- **解決策**: 最終的に成功した方法
- **根本原因**: なぜこのエラーが起きたか（1行）
- **信頼度**: 1
```
カテゴリ: `[Next.js]` `[Supabase]` `[LINE/LIFF]` `[Claude Code]` `[TypeScript]` `[Tailwind/CSS]` `[Git/Deploy]` `[API連携]` `[npm/依存関係]` `[その他]`

#### best-practices.md カテゴリ
- `## コーディングパターン` - パターン名: 説明
- `## ディレクトリ構造` - 配置ルール: 説明
- `## ユーティリティ・ライブラリ` - ライブラリ名: 用途と使用例
- `## 注意点・落とし穴` - 問題: 解決策（**アンチパターンはここ**）
- `## 外部サービス連携` - サービス名: 設定・使い方
- `## 自動化・cron運用` - パターン: 説明
- `## その他` - カテゴリ不明なものはここ

各エントリは `- [YYYY-MM-DD] 項目名: 説明 (信頼度: 1)` の形式。**末尾の `(信頼度: 1)` は省略不可**。

> 💡 **将来的なリファクタ**: best-practices.md が500行を超えたり、エントリ数が30〜40件を超えたら、カテゴリ別ファイルへの分割を検討する。例: `~/.claude/docs/best-practices/api-image-generation.md` `~/.claude/docs/best-practices/notion-api-integration.md` 等。元の best-practices.md は索引化（リンク集）にする。

`~/.claude/docs/best-practices.md` が存在しない場合は、まず以下のテンプレートで初回作成:

```markdown
# ベストプラクティス集

開発で得た知見を蓄積。全プロジェクトで参照可能。

## コーディングパターン

## ディレクトリ構造

## ユーティリティ・ライブラリ

## 注意点・落とし穴

## 外部サービス連携

## 自動化・cron運用

## その他
```

#### skill-health.md フォーマット
```markdown
### [スキル名] 問題の簡潔な説明
- **発生日**: YYYY-MM-DD
- **案件**: プロジェクト名
- **症状**: 何が期待と違ったか
- **原因推定**: モデル変化 / 環境変化 / トリガー不一致 / 指示の曖昧さ
- **ステータス**: 未対応 / SKILL.md修正済み / 解消確認済み
- **信頼度**: 1
```

### Step 4: 短い報告
追記後、ユーザーに **1〜2行で報告**:
> 💾 学びを保存: `error-solutions.md` に「[Supabase] RLS Storage upsert権限」を追記しました

## 発火しない場面（重要 — 無駄な書き込みを避ける）

**以下は完全にスキップする**。ファイル読み込みも追記もしない:

- 一回で解決した自明なエラー（試行錯誤なし）
- 既に best-practices.md / error-solutions.md に記載がある内容（grep で必ず確認）
- 一時的な実験・スクラッチコード
- ユーザーへの質問・確認・対話のみ
- ドキュメントを読んだだけ・記事をアーカイブしただけ
- 既知の操作（コミット・プッシュ・デプロイ等）の繰り返し
- セッションがレビュー・整理・調査だけで終わった場合

**判断基準**:
- 「この知見は3ヶ月後の別プロジェクトで本当に役立つか？」を問う
- 答えが No なら発火しない
- 答えが Yes でも既に記載があれば発火しない
- **「念のため記録」は禁止**。重複・低価値追記はファイルを汚すだけ

「学びがなかった」は正常な結果。無理に何かを記録しなくていい。

## /clear-prep との関係

`/clear-prep`（コンテキストクリア前の引き継ぎコマンド）が手順0で `/learn` を呼び出す。
セッション中に発火し損ねた学びがあっても、/clear-prep が安全網として最後にもう一度チェックする。

## 追記例（参考）

**末尾の `(信頼度: 1)` は必須**。再発時に `(信頼度: 2 ⚠️ 再発)` → `(信頼度: 3 🔴 強い知見)` と昇格させる。

```markdown
## コーディングパターン
- [2026-04-28] Result型: try-catchではなくResult型でエラーハンドリング (信頼度: 1)

## 注意点・落とし穴
- [2026-04-28] Supabase Storage upsert: INSERT権限だけだと既存ファイル更新失敗。UPDATE権限も必要 (信頼度: 2 ⚠️ 再発)

## 外部サービス連携
- [2026-04-28] Vercel環境変数: Sensitiveフラグ漏れがあるとVercel侵害時に値が読まれる (信頼度: 1)
```

## 重要な設計思想

**「セッション終了を待たない」**:
- /clear-prep に頼ると、/clear せずに終わった場合に学びが消える
- 発見した瞬間に保存することで、引き継ぎ忘れリスクをゼロにする
- 1セッションで複数回発火してOK

**「短い報告で煩わしさを減らす」**:
- 詳細な提案や承認待ちは不要
- 1〜2行の保存通知で済ませる（ユーザーが後で確認できる）
- 案件固有のドメイン知識のみ「プロジェクトCLAUDE.mdに追記しますか？」と確認

**「Claude Code を案件をこなすほど賢くする」**:
- 1案件目: 一般的な開発スキル
- 5案件目: あなた特有のパターン・落とし穴・解決策が蓄積
- 10案件目: 似たような案件で「前回どう解決したか」が即座に参照される
- これが Boris Cherny 推奨の「Plan → Verify → **Persist** → Automate」の Persist 層
